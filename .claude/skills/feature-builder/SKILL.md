# Feature Builder - 피처 개발 워크플로우

Notion 기획 문서에서 시작하여 PRD 작성, HTML 목업 검증, Tech Spec, 구현까지 7단계로 진행하는 체계적인 피처 개발 워크플로우입니다.

## Arguments

- `$0`: Notion 페이지 ID 또는 URL (컨텍스트 소스)
- `$1`: 기능 타이틀명 (PRD/Tech Spec 파일명에 사용)

## 공통 규칙

1. **매 Phase 완료 시 반드시 사용자 승인을 받은 후** 다음 Phase로 진행합니다.
2. **승인 루프**: 작성 → 셀프 리뷰 → 사용자 리뷰 → (피드백 시 수정 반복) → 승인 → 다음 Phase
3. **프로젝트 호환성**: 각 Phase 시작 시 현재 프로젝트의 기술 스택과 구조를 확인합니다. 프로젝트 특성에 맞지 않는 부분이 있으면 경고하고, 프로젝트에 맞는 수정안을 제시합니다.
4. **문서 저장 위치**: `docs/` 폴더에 저장합니다.
5. **날짜**: `sh`를 통해 오늘 날짜를 확인합니다.
6. **진행 상황 추적**: TaskCreate/TaskUpdate로 각 Phase의 진행 상황을 추적합니다.

## 셀프 리뷰 참여자

### PRD 리뷰 (Phase 1-3)
1. **Denis** (비즈니스 리드): 비즈니스 가치, ROI, 시장 적합성 관점
2. **Bitsaion** (프로덕트 리드): 사용자 경험, 기능 범위, 우선순위 관점
3. **Zhihuan** (디자인 리드): UI/UX, 접근성, 디자인 시스템 정합성 관점

### Tech 리뷰 (Phase 4-6)
1. **Denis** (프론트엔드 엔지니어): 컴포넌트 설계, 상태 관리, 기존 공통 컴포넌트 재사용 관점
2. **Bitsaion** (백엔드 엔지니어): API 설계, DB 쿼리 성능, 도메인 로직 분리 관점
3. **Zhihuan** (테크 리드): 전체 아키텍처, PRD 요구사항 반영 여부, 의존성/사이드 이펙트, 유지보수성 관점

## Phase 1: 컨텍스트 수집 및 PRD 초안

### 목표
신규 기능의 초기 컨텍스트를 수집하고 PRD 초안 (Context, Goals/Non-Goals, Success Definition)을 작성합니다.

### 절차

1. **기능 이름 확인**: 사용자에게 기능 이름(가칭)을 확인합니다. ($1이 제공된 경우 해당 값 사용)

2. **Notion 컨텍스트 수집**:
   - $0이 제공된 경우: Notion MCP를 통해 해당 페이지에서 `$1` 타이틀 산하 내용을 읽어옵니다.
   - $0이 없는 경우: 사용자에게 기획 컨텍스트(Notion, 회의록, Slack 등)를 직접 제공받습니다.

3. **프로젝트 구조 탐색**: 현재 코드베이스를 탐색하여 기술 스택, 디렉토리 구조, 관련 기존 코드를 파악합니다.

4. **추가 컨텍스트 요청**: 참고할 추가 자료(Figma, 디자인 시안, 참고 서비스 등)가 있는지 사용자에게 요청합니다.

5. **PRD 문서 생성**: `templates/prd-template.md`를 기반으로 `docs/prd/{YYMMDD}-{featureName}.md` 파일을 생성합니다.

6. **PRD 초안 작성**: Context, Goals/Non-Goals, Success Definition 섹션만 작성합니다. 나머지 섹션은 비워둡니다.

7. **셀프 리뷰**:
   ```
   Denis, Bitsaion, Zhihuan이 Context, Goals/Non-Goals, Success Definition을 보고
   더 나은 내용을 위해 토론하는 모습을 시뮬레이션해. 그 결과를 바탕으로 PRD 초안을 업데이트해.

   1. Denis (비즈니스 리드): 비즈니스 가치와 시장 적합성 관점에서 검토
   2. Bitsaion (프로덕트 리드): 사용자 경험과 기능 범위 관점에서 검토
   3. Zhihuan (디자인 리드): 구현 가능성과 디자인 관점에서 검토
   ```

8. **사용자 리뷰 요청**: PRD 초안의 주요 내용을 요약하고 검토를 요청합니다. "PRD 초안입니다. 기획 의도가 명확하게 담겼는지, 특히 MVP 범위가 적절한지 검토 부탁드립니다."

9. **승인 루프**: 피드백 반영 → 재검토 → 승인 시 Phase 2로 이동

---

## Phase 2: 요구사항 정의

### 목표
PRD의 Requirements 섹션을 상세하게 정의합니다. Must-have와 Nice-to-have 우선순위를 구분합니다.

### 절차

1. **요구사항 초안 작성**: Phase 1에서 승인된 PRD를 읽고 Requirements 섹션 (Must-have, Nice-to-have) 목록을 작성합니다.

2. **셀프 리뷰**:
   ```
   Denis, Bitsaion, Zhihuan이 Requirements를 보고 더 나은 요구사항 정의를 위해 토론해.

   1. Denis (비즈니스 리드): "이 요구사항들이 비즈니스 목표를 충분히 달성할 수 있나?"
   2. Bitsaion (프로덕트 리드): "Must-have와 Nice-to-have 구분이 적절한가? 빠진 기능은 없나?"
   3. Zhihuan (디자인 리드): "사용자 관점에서 빠진 요구사항이 있는가? 접근성은 고려되었나?"
   ```

3. **사용자 리뷰 요청**: "요구사항 초안입니다. 우선순위 구분이 적절한지 검토 부탁드립니다."

4. **승인 루프**: 피드백 반영 → 재검토 → 승인 시 Phase 3으로 이동

---

## Phase 3: UX 정의 및 HTML 목업

### 목표
UX Acceptance Criteria, User Flows를 정의하고, HTML/CSS 목업을 만들어 시각적으로 검증합니다.

### 절차

1. **UX 관련 섹션 초안 작성**: Requirements를 바탕으로 UX Acceptance Criteria, User Flows (Mermaid.js) 섹션을 작성합니다.

2. **HTML/CSS 목업 생성**:
   - `docs/mockups/{featureName}.html` 파일을 생성합니다.
   - 프로젝트의 기존 디자인 시스템/스타일을 참고하여 핵심 화면을 HTML/CSS로 구현합니다.
   - 반응형 레이아웃, 주요 상호작용 상태 (기본, 호버, 에러 등)를 포함합니다.
   - 목업 파일은 별도 의존성 없이 브라우저에서 바로 열 수 있어야 합니다.

3. **셀프 리뷰**:
   ```
   Denis, Bitsaion, Zhihuan이 UX Acceptance Criteria, User Flows, HTML 목업을 보고
   더 나은 UX를 위해 토론해.

   1. Denis (비즈니스 리드): "비즈니스 목표가 UX에 잘 반영되었나?"
   2. Bitsaion (프로덕트 리드): "사용자 흐름에 빠진 시나리오가 없나? 엣지 케이스는?"
   3. Zhihuan (디자인 리드): "목업의 레이아웃과 인터랙션이 적절한가? 접근성 이슈는 없나?"
   ```

4. **사용자 리뷰 요청**: 목업 파일 경로를 안내합니다. "HTML 목업을 생성했습니다. 브라우저에서 `docs/mockups/{featureName}.html`을 열어 확인해주세요. 화면 구성이 의도한 것과 맞는지 검토 부탁드립니다."

5. **승인 루프**: 피드백 반영 (HTML 수정 포함) → 재검토 → 승인 시 Phase 4로 이동

## Phase 4: 의존성 분석 및 기술 설계

### 목표
Tech Spec 문서를 생성하고, 코드베이스 전반에 미치는 기술적 영향을 분석합니다.

### 절차

1. **Tech Spec 문서 생성**: `templates/tech-spec-template.md`를 기반으로 `docs/tech-spec/{YYMMDD}-{featureName}-spec.md` 파일을 생성합니다.

2. **프로젝트 호환성 검사**:
   - 프로젝트의 아키텍처 패턴을 확인합니다 (예: Feature-Sliced Design, Layered Architecture 등).
   - 사용 중인 기술 스택을 확인합니다 (프레임워크, 상태 관리, DB 등).
   - **맞지 않는 부분이 있으면 경고하고, 프로젝트에 맞는 대안을 제시합니다.**

3. **코드베이스 분석**: PRD 요구사항 구현을 위해 수정/생성이 필요한 파일 및 DB 테이블 목록을 도출합니다.

4. **기술 분석 초안 작성**: 의존성 분석 및 기술 설계 섹션을 작성합니다 (API, DB, Domain, UI, Release Strategy).

5. **셀프 리뷰**:
   ```
   Denis, Bitsaion, Zhihuan이 기술 분석 초안을 리뷰하며 토론해.

   1. Denis (프론트엔드 엔지니어): "API 응답으로 필요한 데이터를 한 번에 받을 수 있나?
      상태 관리는 어떻게? 기존 공통 컴포넌트를 재사용할 수 있나?"
   2. Bitsaion (백엔드 엔지니어): "이 쿼리는 데이터가 많아지면 성능 문제가 없나?
      도메인 로직이 너무 복잡해지지 않나? 서비스 레이어를 더 분리해야 하나?"
   3. Zhihuan (테크 리드): "전체 아키텍처 관점에서 문제는 없나? PRD의 모든 요구사항이
      반영되었나? 놓친 의존성이나 사이드 이펙트는 없나?"
   ```

6. **(조건부) DB 스키마 변경 시**:
   ```
   Bitsaion과 Zhihuan이 DB 스키마 변경의 장단점과 위험성에 대해 토론해.

   1. Bitsaion (백엔드 엔지니어, 새로운 기술 도입에 긍정적)
   2. Zhihuan (테크 리드, 안정성과 유지보수 가능성, 롤백 계획을 최우선으로 고려)
   ```

7. **사용자 리뷰 요청**: "기술 분석 초안입니다. DB 스키마 변경 관련 부분이 있다면 특히 확인이 필요합니다."

8. **승인 루프**: 피드백 반영 → 재검토 → 승인 시 Phase 5로 이동

## Phase 5: 실행 계획 수립

### 목표
개발 Task를 Phase 단위로 나누고, 체크리스트 형태로 구체화합니다. 테스트 계획도 수립합니다.

### 절차

1. **실행 계획 초안 작성**: Plan 섹션 (Phase별 체크리스트)과 테스트 계획 섹션을 작성합니다.
   - **핵심 기본 플로우 검증**: 기존 핵심 기능이 이번 변경으로 깨지지 않는지 확인하는 테스트
   - **신규 피처 플로우 검증**: PRD에 정의된 User Flow가 기획 의도대로 동작하는지 검증하는 테스트

2. **셀프 리뷰**:
   ```
   Denis, Bitsaion, Zhihuan이 Plan과 테스트 계획을 리뷰해.

   1. Denis (프론트엔드 엔지니어): "Phase별로 작업이 잘 나뉘었나? 기존 컴포넌트
      활용 계획이 포함되었나? 핵심 사용자 흐름을 검증하는 테스트가 구체적인가?"
   2. Bitsaion (백엔드 엔지니어): "백엔드와 프론트엔드 작업 간 의존성 순서가 명확한가?
      API 명세가 확정되어야 프론트에서 시작할 수 있는 부분은 선행되는가?"
   3. Zhihuan (테크 리드): "가장 핵심적이고 되돌리기 어려운 작업이 우선 처리되는가?
      각 Phase가 독립적으로 검증 가능한 단위인가?"
   ```

3. **사용자 리뷰 요청**: "실행 계획 및 테스트 계획 초안입니다. 개발 Task와 테스트 범위가 적절한지 검토 부탁드립니다."

4. **승인 루프**: 피드백 반영 → 재검토 → 승인 시 Phase 6으로 이동

## Phase 6: 데이터 흐름 및 리스크 관리

### 목표
핵심 로직별 데이터 흐름을 정의하고, 잠재적 리스크와 롤백 계획을 수립합니다.

### 절차

1. **데이터 흐름 및 리스크 초안 작성**: 데이터 흐름 및 테이블 명세, API 명세 (필요 시), Risk & Rollback 섹션을 작성합니다.

2. **셀프 리뷰**:
   ```
   Bitsaion과 Zhihuan이 데이터 흐름과 리스크 관리 계획을 리뷰해.

   1. Bitsaion (백엔드 엔지니어): "데이터 흐름이 명확한가? 각 테이블의 역할(Read/Write)이
      정확히 명시되었나? API 명세는 프론트엔드 개발자가 혼동 없이 사용할 수 있을 정도로
      구체적인가?"
   2. Zhihuan (테크 리드): "유지보수 관점에서, 3개월 뒤 다른 개발자가 이 코드를 봤을 때
      데이터 흐름을 쉽게 이해할 수 있나? 불필요한 복잡성은 없나? 기술 부채를 남기지 않는가?"
   ```

3. **사용자 리뷰 요청**: "데이터 흐름과 리스크 관리 계획 초안입니다. 개발 전 최종 검토 부탁드립니다. 이 테크 스펙을 바탕으로 개발을 시작해도 될까요?"

4. **승인 루프**: 피드백 반영 → 재검토 → 최종 승인 시 Phase 7로 이동

## Phase 7: 구현

### 목표
컨펌된 Tech Spec을 기반으로 실제 코드를 작성합니다.

### 절차

1. **구현 시작 안내**: "테크 스펙이 최종 확정되었습니다. 이제 구현을 시작합니다."

2. **프로젝트 특성 확인**:
   - 프로젝트에 테스트 프레임워크가 설정되어 있는지 확인합니다.
   - 프로젝트의 코딩 컨벤션을 확인합니다.
   - **TDD가 적합하지 않은 프로젝트인 경우, 일반 구현 순서를 제안합니다.**

3. **Tech Spec Plan에 따라 Phase별 구현**:
   - 각 Phase의 체크리스트를 순서대로 구현합니다.
   - Phase 완료 시마다 사용자에게 진행상황을 공유합니다.
   - 구현 중 Tech Spec과 다른 판단이 필요한 경우 사용자에게 확인합니다.

5. **최종 검증**:
   - 빌드 확인
   - 린트 확인
   - 테스트 통과 확인 (테스트가 있는 경우)

6. **목업 파일 정리**:
   - 사용자에게 확인합니다: "`docs/mockups/{featureName}.html` 목업 파일을 삭제할까요?"
   - 삭제 동의 시: `powershell Remove-Item` 으로 파일 삭제 후 확인합니다.
   - 삭제 거절 시: `docs/mockups/`에 그대로 보관합니다.

7. **Git 커밋 및 Push**:
   - PR 없이 `git add → commit → push` 로 직접 main에 반영합니다.
   - 커밋 메시지는 `feat:` / `fix:` / `refactor:` 등 prefix를 붙여 간결하고 명료하게 작성합니다.
   - 커밋 메시지는 사용자에게 별도로 묻지 않고 Claude가 자율적으로 작성합니다.
   - 스테이징은 관련 파일을 명시적으로 지정합니다 (`git add -A` 사용 금지).
   - 목업 파일을 삭제한 경우 해당 삭제도 커밋에 포함합니다.

8. **구현 완료 안내**: "구현 및 Push가 완료되었습니다."

## 프로젝트 호환성 경고 패턴

Phase 4 시작 시 아래 항목을 체크하고, 맞지 않는 부분이 있으면 사용자에게 경고합니다:

- **아키텍처 패턴**: 프로젝트의 디렉토리 구조와 패턴을 분석. Feature-Sliced Design, Layered, MVC 등
- **상태 관리**: 사용 중인 상태 관리 라이브러리/패턴 확인 (SWR, React Query, Zustand, Context 등)
- **스타일링**: CSS 방식 확인 (Tailwind, CSS Modules, styled-components 등)
- **테스트**: 테스트 프레임워크 존재 여부 (Jest, Vitest, Cypress 등)
- **DB/API**: 사용 중인 DB와 API 패턴 확인

경고 예시:
> **프로젝트 호환성 경고**: 이 프로젝트는 Feature-Sliced Design을 사용하지 않습니다. 현재 프로젝트의 디렉토리 구조(`src/components/`, `src/pages/`)에 맞게 파일 위치를 조정합니다.
